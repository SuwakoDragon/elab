## 互联网是什么？

互联网已成为全球设备间数据传输的普遍工具。本课程将重点介绍支撑这一过程的基础设施。

互联网和万维网并非同一概念。你可以把万维网理解为构建在互联网之上的应用程序（例如 Facebook、Twitter），你可以通过网络浏览器（例如 Firefox、Chrome）访问这些应用程序。除了万维网之外，其他应用程序也可以使用互联网基础设施。非万维网应用程序的例子包括在线游戏，甚至是物联网 (IoT) 设备，例如冰箱或汽车中的传感器。

## Intro

### （一）互联网的层次

在本节中，我们将自下而上地构建互联网，从基本构建模块入手，将它们组合起来形成互联网基础设施。我们将以邮政系统为例进行类比，因为它与互联网在设计上有很多相似之处。

#### 第 1 层：物理层

首先，我们需要某种方式将信号传递到太空。在邮政系统中，这可以是邮递员、驿马快信、卡车、信鸽等等。

在互联网领域，我们正在寻找一种跨越空间传输比特（1 和 0）信号的方法。这项技术可以是电线上的电压、无线电波、光纤电缆上的光脉冲等等。电子工程领域有很多专门研究跨越空间传输信号的分支，但本课程我们不打算深入探讨。

#### 第 2 层：链路层

打个比方，既然我们现在有了跨越空间传输数据的方法，就可以利用这个基本要素连接两户人家。我们甚至可以尝试连接镇上所有的房屋。

在互联网中，**链路**连接两台机器。该链路可以使用任何类型的技术（有线、无线、光纤等）。如果我们使用链路连接许多附近的计算机（例如7舍320的所有计算机），我们就得到了一个**局域网（LAN）**。

在第二层，我们还可以将比特分组为称为**数据包**（有时在这一层也称为帧）的数据单元，并定义数据包在物理信号中的起始和结束位置。我们还可以处理诸如多人同时使用同一根线路发送数据之类的问题（多路复用…当然这偏信通了）。

链路层的工作是一次通过一条链路传输数据。你可能听说过以太网和 WiFi——这两个是不同链路层的例子。

#### 第 3 层：网络层

我们现在有办法将同一区域内的所有人连接起来，但如果不同区域内的两个人想要交流呢？一种可能的办法是在不同的本地网络之间添加大量连接，但这似乎效率不高。（如果这两个本地网络位于不同的洲呢？）

更明智的做法是在每个网络中都设立一个邮局，然后将两个邮局连接起来。这样，如果网络 A 中的某人想要与网络 B 中的某人通信，他们可以将邮件寄到网络 A 的邮局。该邮局会将邮件转发到网络 B 的邮局，由网络 B 的邮局将邮件送达目的地。

#### 网络之网络

互联网常被描述为**网络之网络**。它由许多小型局域网组成，每个局域网内部的事务都可以在本地进行管理（例如由大连理工大学管理）。然后，所有这些局域网可以相互连接，最终形成互联网。

在网络中，不同的链路可能使用不同的二层技术。有些链路可能使用有线以太网，而另一些链路可能使用光纤或无线蜂窝技术。在二层，我们利用特定网络技术，在本地网络中通过链路发送数据包。然后在三层，我们利用链路发送数据包的能力，将数据包发送到互联网上的任何位置。数据包在跨越不同网络的过程中，可能会经过多种不同类型的链路。

在我们的比喻中，我们可以看到家庭和邮局之间的区别。家庭之间互寄信件，而邮局本身并不寄送或接收邮件，但它们帮助连接其他家庭。

在互联网中，**终端主机**是指通过互联网进行通信的机器（例如服务器、笔记本电脑、手机）。与之相对，**交换机**（也称为**路由器**）本身并不发送或接收数据，而是帮助终端主机彼此通信。例如，您家中的路由器，或者互联网服务提供商（例如 AT&T）部署的大型路由器，都是交换机。

#### 第三层：尽力而为服务模式

我们似乎已经构建了一个可以向世界任何地方发送数据的系统，那么为什么不就此止步呢？Layer 3 还有两个问题需要我们解决。

第一个问题涉及第三层服务模型。如果您使用第三层基础设施通过互联网发送消息，那么网络会为您提供什么样的服务模型？您可以将服务模型理解为网络与用户之间的一份契约，它描述了网络支持和不支持的功能。

实际服务模型的示例可能包括：网络保证数据传输；或者，网络保证在一定时限内传输数据；或者，网络不保证数据传输，但承诺在传输失败时报告错误。

互联网的设计者并不支持上述任何一种模型。相反，互联网只支持**尽力而为的**数据传输。如果您通过第三层（数据交换层）发送数据，互联网会尽力尝试传输，但无法保证数据一定能够成功送达。互联网也不会告知您数据传输是否成功。

这可能会让人感到意外。当数据包无法保证送达时，互联网怎么可能正常运作？如果应用程序希望保证其数据在必要时会被重传，并且会按顺序且无损坏地交付给应用程序，那么它需要运行在 IP 之上的其他协议。这就是传输层的工作......

为什么设计者会选择如此弱的服务模式？一个主要原因是，构建满足这些较低需求的网络要容易得多。

注意，网络层无需关心链路层如何通过链路发送数据报。事实上，不同的链路层在非常不同的环境中工作;以太网和 WiFi 显然差别很大。网络层和链路层之间的关注点分离，使双方能够专注于自己的工作，而无需担心对方的工作。这也意味着单个网络层可以通过简单地将数据报交给多个链路层发送，从而与它们通信。这种关注点的分离可能得益于每一层的模块化以及与下层共享的明确定义 API。

#### 第三层：数据包抽象

到目前为止，在第三层之前，我们一直考虑的是通过互联网独立发送每条消息。更正式地说，第三层数据传输的主要单元是数据**包**，它是由一小段字节组成的数据，作为一个整体在互联网上传输，并在路由器之间来回跳转。

第三层面临的第二个问题是：数据包大小有限。如果应用程序需要发送大量数据（例如视频），我们需要将这些数据分割成数据包，然后分别通过网络发送每个数据包。

通过这种数据包抽象，我们现在可以观察数据包在网络中传输的整个过程。发送方将数据拆分成单个数据包。数据包沿着链路传输并到达交换机。交换机将数据包转发到目的地，或者转发到距离目的地更近的另一个交换机。数据包在一个或多个交换机之间跳跃，每个交换机都将其转发得更近，直到最终到达目的地。需要注意的是，由于采用的是尽力而为模型，任何交换机都可能丢弃数据包，因此无法保证数据包一定能到达目的地。

互联网由终端主机、链路和路由器组成。数据通过每条链路逐跳传递。数据以数据包形式传递。一个数据包包含我们希望被传递的数据，以及一个头部，告诉网络数据包将被送到哪里、从哪里来。

除了基本的不可靠、尽力而为的无连接数据报服务外，IP 还提供一些经过精心挑选的其他服务。知识产权的设计者非常努力地在提供最基本的沟通功能与不提供过于基础的服务之间找到平衡，以至于通信功能失效。

首先，IP 试图防止数据包无限循环。由于 IP 路由器通过互联网逐跳转发数据包，路由器中的路由表可能出现错误，导致数据包开始沿着同一路径循环。这种情况最可能发生在路由表发生变化时，它们暂时处于不稳定状态。IP 不是试图防止环路发生——这需要非常复杂的操作——而是采用一种非常简单的机制来捕捉并删除看似陷入循环的数据包。为此，IP 只需在每个数据报的头部添加一个跳数字段。这被称为TTL（time to live）。它从大约 128 开始，然后经过的每个路由器都会递减。如果数据报值降到零，IP 会判断自己陷入了循环，路由器会丢弃数据报。这是一种典型的 IP 机制——它并不保证不会发生环路，只是试图限制网络中无休止循环数据包洪流造成的损害。当然好像会在1/2、1/4……时询问，不一定等到128.

如果数据包太长，IP 会对数据包进行分段处理。IP 设计成可以在任何类型的链路上运行。大多数链路对其可携带的数据包大小都有限制。例如，以太网只能携带长度小于 1500 字节的数据包。如果一个应用需要发送超过 1500 字节，必须将其拆分成 1500 个部分，然后才能发送 IP 数据报。现在，在通往目的地的路径上，一个 1500 字节的数据报可能需要通过一条只能携带较小数据包（例如 1000 字节）的链路。连接两条链路的路由器会将数据报分成两部分。以太网只能携带长度小于 1500 字节、更小的数据报数据包。IP 提供了一些头字段，我们马上会看到，帮助路由器将数据报分割成两个自包含的 IP 数据报，同时提供终端主机正确重组数据所需的信息。

IP 使用头部校验和以降低数据报送错目的地的可能性。IP 在数据报头中包含校验和字段，以确保数据报被送达到正确的位置。如果由于路由器的错误，数据包意外且频繁地发送到错误的地方，可能会成为相当严重的安全问题。

网络层的工作是从互联网端到端地从源到目的地传输数据包。

#### 第四层：传输层

目前我们已经在第三层发现了两个问题。大数据必须被分割成数据包，而IP协议只能尽力而为。

为了解决这两个问题，我们将引入一个新的层，即**传输层**。该层以第 3 层为基础，并实现了一个额外的协议，用于重发丢失的数据包、将数据拆分成数据包以及重新排序乱序到达的数据包（以及其他功能）。

传输层协议使我们能够不再以数据包的角度思考，而是以**流**的角度思考，即在两个端点之间交换的数据包流。

最常见的传输层是 TCP 协议，或称传输控制协议。（你可能听说过 TCP/IP，指的是应用程序TCP 和 IP 合用）。TCP 确保互联网一端应用发送的数据能够正确地以正确的顺序传递到另一端的应用。如果网络层丢弃了一些数据报，TCP 会重新发送这些数据报，必要时会多次。如果网络层传递数据顺序错误——可能是因为两个数据包走了不同的路径——TCP 会将数据重新排列到正确的顺序。在后续视频中，你会学到很多关于 TCP 及其工作原理的内容。目前最重要的是，TCP 为应用程序提供一种服务，保证数据的正确顺序传输，运行在网络层服务之上，而网络层服务则提供不可靠的数据报分发服务。

你应该能想象，像网页客户端或电子邮件客户端这样的应用程序，确实觉得 TCP 非常有用。通过使用 TCP 确保数据正确传递，他们无需担心在应用内实现所有机制。他们可以利用开发者为正确实现 TCP 所付出的巨大努力，并重复利用这些努力来正确传递数据。重复使用是分层的另一个重要优势。

但并非所有应用都需要数据正确交付。例如，如果视频会议应用以数据包形式发送视频片段，等待数据包多次重传可能没有意义;最好还是继续前行。有些应用根本不需要 TCP 服务。

如果应用程序不需要可靠的交付，它可以使用更简单的 UDP——用户数据报协议。UDP 只是把应用数据打包起来，交给网络层再传输到另一端。UDP 不提供送达保证。换句话说，应用至少可以选择两种不同的传输层服务：TCP 和 UDP。实际上还有许多其他选择，但这些是最常用的传输层服务。



#### 第七层：应用层

在互联网之上构建应用层是一种强大的设计选择。如果我们在底层构建专门用于在终端主机之间传输视频的基础设施，那么电子邮件客户端就必须构建自己独立的邮件传输基础设施。互联网的设计使其成为适用于任何类型应用数据的通用通信网络。

在本课程中，我们将更侧重于支撑应用层的基础设施（例如邮递员、邮局），而较少关注应用本身（例如邮件内容）。

现在我们已经了解了所有层级，请注意每一层都依赖于其下一层提供的服务，同时也为其上一层提供服务。例如，编写第 7 层（应用层）协议的人可以假设他们已经从第 4 层获得了可靠的数据传输。他们不必担心单个数据包丢失，因为这是第 4 层已经处理的问题。

两层之间通过接口直接交互。实际上，没有办法跳过某些层，例如，在第三层之上构建第七层。

注：您可能已经注意到我们跳过了第 5 层和第 6 层。在 20 世纪 70 年代，当这些层最初被标准化时，设计者认为这些层是必要的，但它们在现代互联网中已经过时了。如果您感兴趣，会话层（第 5 层）的作用是将不同的数据流组合成一个会话（例如，加载各种图像和广告以形成网页），而表示层（第 6 层）的作用是帮助用户可视化数据。如今，这些层的功能大多已在第 7 层中实现。

### （二）报头

#### 为什么需要报头？

在上一节中，我们看到在第三层（网络层），数据以数据包的形式在互联网上传输。假设一个应用程序想要通过互联网发送一个文件。我们可以提取图像中的一些比特，将它们打包成一个数据包，然后通过互联网发送出去。当交换机接收到这串 1 和 0 时，它并不知道该如何处理这些比特。

打个比方，如果我写封信给朋友，然后交给邮局，邮局就不知道该怎么处理这封信了。我们应该把信装进信封，并在信封上写一些信息（比如我朋友的地址），告诉邮局该如何处理这封信。

就像信封一样，当我们发送数据包时，需要附加一些元数据来告诉网络基础设施如何处理这个数据包。这些额外的元数据被称为**数据包头部**。其余部分（例如，要发送的文件、信封里的信件）被称为**有效载荷**。

打个比方，邮局不应该读取信件的内容，而应该只读取信封上的信息来决定如何寄送。同样，网络基础设施也应该只读取邮件头信息来决定如何传输数据。

收件人关心的是信件的内容，而不是信封。同样，终端主机上的应用程序关心的是有效载荷，而不是头部。尽管如此，终端主机仍然需要了解头部信息，以便在发送数据包之前添加头部。

请注意，随着我们向较低抽象层移动，我们在数据周围包裹了更多头部信息。然后，随着我们向较高抽象层移动，我们从数据上剥离了更多层。

![1-15-multiheader6](C:\Users\Dragon\Desktop\demo\images\1-15-multiheader6.png)

每一层只需要解自身的头部信息，并且（在某种意义上）与同一层的其他层进行“沟通”。当A秘书在信封上写下名字时，那是给B秘书看的（而不是给邮递员或老板看的）。

![1-16-wrapping-unwrapping](C:\Users\Dragon\Desktop\demo\images\1-16-wrapping-unwrapping.png)

更正式地说，在互联网上，同一层的节点通过在该层建立协议进行通信。该协议仅对该特定层的实体有意义。

![1-17-layer-peers](C:\Users\Dragon\Desktop\demo\images\1-17-layer-peers.png)

请注意，某些层提供多种协议选择（例如，第二层提供无线或有线协议）。在这种情况下，通信双方必须使用相同的协议。有线发送方无法与无线接收方通信。

小结：

**分层**

网络工程师发现将构成互联网的所有功能整理成*层*很方便。比如 BitTorrent、Skype 或万维网，它会与目的地的对等层通信。当应用程序有数据可发送时，它会将数据交给传输层，后者负责可靠（或不可靠）地将数据传递到另一端。传输层通过将数据交给网络层来向另一端发送数据，后者负责将数据拆分成数据包，附带正确目的地地址。最后，数据包交给链路层，链路层负责沿路径从一跳传递到下一跳。

--我们毕竟不需要从种小麦开始做面包。分层是对上层的保护、对整个通信流程的抽象。

--我们可以根据对网络的分层抽象横向看待信号的流动。简化了互联网。

**协议**

--发送方机器上的代码和接收方机器上的代码都需要就数据格式以及对不同消息的响应方式达成一致。我们还需要考虑各种极端情况、漏洞和恶意行为。

--本课程中，我们将学习许多已在互联网上标准化的协议。

### （四）地址

前面我们说过，报头需要包含收件人的地址。那么，这个地址究竟是什么呢？简单来说，网络地址是指一个值，它告诉我们主机在网络中的位置。

当我们更详细地观察不同的层级时，会发现不同层级的地址格式各不相同。例如，如果您想寄信到综一，您可以将收件地址写成综一，学校里的人都知道该把信送到哪里。相比之下，如果您想从校外寄信，则必须写出完整的街道地址，例如“凌工路2号”。
**这也就是所谓的公网地址。**

同样，互联网的不同层级采用不同的寻址方案，以更好地服务于该层级。例如，有时主机使用其人类可读的名称（例如 www.google.com）来指代。有时，同一主机使用机器可读的 IP 地址（例如 74.124.56.2）来指代，其中 IP 地址编码了服务器位置的信息（如果服务器移动，该地址可能会改变）。有时，同一主机可以使用其硬件 MAC 地址来指代，该地址始终保持不变。

随后我们会稍微详细地介绍IP地址。

### （五）在主机和路由器上的层

![1-19-layers-host-routers](C:\Users\Dragon\Desktop\demo\images\1-19-layers-host-routers.png)

还是以邮政系统为例：互联网不仅仅是发送方和接收方。除了这两个终端主机之外，还有路由器将数据包转发经过多跳到达目的地。我们的分层和报头概念如何在所有这些机器之间相互作用呢？

终端主机需要实现所有层。你的电脑需要了解第七层（网络层）才能运行网页浏览器。你的电脑还需要了解第一层（网络层）才能通过网络传输数据。此外，你还需要中间的所有层，才能将应用层数据（例如老板的信）传递到物理层。

那么路由器呢？路由器确实需要第 1 层（通信层）来接收线路上的数据，第 2 层（网络层）来发送线路上的数据包，以及第 3 层（通信层）来在全球网络中转发数据包。然而，路由器实际上并不需要考虑第 4 层和第 7 层（数据层）。路由器并不运行网页浏览器来显示网页，也不需要考虑可靠性（回想一下，路由器采用的是尽力而为的服务模式）。

接下来我们加入路由器，再探讨一遍数据包传输过程。

首先，主机 A 接收消息，并向下遍历协议栈，为第 7 层、第 4 层、第 3 层、第 2 层和第 1 层添加头部。现在我们得到了一个包含每一层头部的数据包。

第 1 层协议将此数据包的各个部分沿着线路发送到到达目的地途中的第一个路由器。

![1-24-multiheader1](C:\Users\Dragon\Desktop\demo\images\1-24-multiheader1.png)

该路由器必须将数据包转发到下一跳，以便数据包最终到达主机 B。我们知道，在全球网络中转发数据包是网络第三层（数据层）的工作。因此，路由器必须将该数据包解析到网络第三层。

路由器读取并解包第 1 层和第 2 层报头，从而显示其下的第 3 层报头。路由器读取此报头以决定数据包的下一步转发目标。

![1-25-multiheader2](C:\Users\Dragon\Desktop\demo\images\1-25-multiheader2.png)

现在，为了将数据包传递到下一跳，路由器必须再次向下遍历协议栈，重新封装第 2 层和第 1 层报头，然后将这些比特沿着线路发送到下一跳。

![1-26-multiheader3](C:\Users\Dragon\Desktop\demo\images\1-26-multiheader3.png)

每个路由器都会重复这种模式：首先解包第 1 层和第 2 层数据包以显示第 3 层头部，然后重新封装第 2 层和第 1 层头部，最后将数据包发送到下一跳。请注意，所有路由器都不会查看第 3 层协议之后的内容，因为更高层的协议仅由终端主机解析。

![1-27-multiheader4](C:\Users\Dragon\Desktop\demo\images\1-27-multiheader4.png)

最终，数据包到达主机 B，主机 B 逐层解包：第 1 层、第 2 层、第 3 层、第 4 层、第 7 层。主机 B 已成功接收消息！

![1-28-multiheader5](C:\Users\Dragon\Desktop\demo\images\1-28-multiheader5.png)

这种分层方案的一个结果是，每一跳都可以使用不同的二层和一层协议。例如，第一跳可以通过有线链路传输，主机 A 和第一个路由器使用的初始二层和一层报头可以是针对有线协议的。相比之下，后续的跳可以通过无线链路传输，该跳两端路由器使用的二层和一层报头可以是针对无线协议的。

![1-29-layer2-peers](C:\Users\Dragon\Desktop\demo\images\1-29-layer2-peers.png)

更一般地说，我们说过每一层只需要与其同层的对等体通信。现在我们可以看到这一点在所有层中都得到了体现。在第 4 层和第 7 层，两个主机必须使用相同的协议来发送和接收数据包。主机的对等体就是另一个主机。

相比之下，在通信的第1层和第2层，路由器必须与前一跳路由器和下一跳路由器使用相同的协议，这样路由器才能接收来自前一跳的数据包并向下一跳发送数据包。路由器的对等体是其路径上的相邻路由器。

![1-19-layers-host-routers (1)](C:\Users\Dragon\Desktop\demo\images\1-19-layers-host-routers (1).png)

总结起来：每个路由器解析第 1 层到第 3 层，而终端主机解析第 1 层到第 7 层。

### （六）端到端原则

我们为什么将互联网设计成现在这种分层结构？为什么只有主机能理解第 4 层和第 7 层，而路由器却不能？

端到端**原则**为互联网设计提供了智慧和指导。麻省理工学院科学家、互联网架构委员会成员大卫·D·克拉克是这一原则的主要贡献者。他的两篇论文——《系统设计中的端到端论证》（1981）和《DARPA互联网协议的设计理念》（1988）——对互联网设计理念产生了深远的影响。

端到端原则指导着关于网络应该实现哪些功能以及不应该实现哪些功能的讨论。该原则应用范围很广，但我们将重点关注以下问题：我们应该在整个网络中实现可靠性（第 4 层），还是只在终端主机上实现？

现在，我们先考虑一个简单的可靠性协议。主机 A 想向主机 B 发送 10 个数据包，于是它将编号为 1 到 10 的数据包通过网络发送出去。目标是让主机 B 要么接收到所有数据包，要么意识到某些数据包丢失并出现错误（我们暂且忽略错误恢复过程）。

如果我们在网络中实现可靠性，互联网会是什么样子？与我们之前的设想不同，现在每个路由器除了要理解第 1、2 和 3 层之外，还必须理解第 4 层。

在这种新的网络架构下，中间路由器必须可靠地将数据包发送到下一跳。它必须保证下一跳接收到所有数据包，否则路由器必须重新发送丢失的数据包。主机本身并不检查所有数据包是否都被接收，而是依赖网络来确保所有数据包都被接收。

在这种方法中，主机必须信任网络。如果其中一个路由器出现故障，丢包，主机对此也无能为力。

另一种方法是端到端方法，这种方法不在网络中实现可靠性，而是强制两端主机自行确保可靠性。路由器可以丢弃数据包，而验证所有数据包是否都被接收则由两端主机负责。

在端到端架构中，由于可靠性是由终端主机实现的，因此控制权掌握在主机手中。主机仍然可能出现故障并丢包，但这一次，主机有能力自行修复故障。更普遍地说，如果你编写代码，最好能够掌控功能的正确性，而不是依赖于可能出错（且你无法修复其错误）的其他人。

考虑到这种比较，如果我们采用第一种方法，即依赖网络本身的可靠性，那么一旦网络出现故障，我们就无法保证绝对的可靠性。最终，终端主机很可能还是会进行端到端检查（就像第二种方案那样）。

在旧式互联网中，每个链路都实现了可靠性。然而，正如我们所见，现代互联网仅在网络中实现尽力而为，并强制终端主机实现可靠性，这符合端到端原则。

综上所述：为了确保正确性，某些应用需求必须实现端到端。此外，端到端实现本身就足够了，无需网络提供额外的支持。由于端到端实现本身就足够了，添加网络功能只会引入不必要的复杂性（和成本），而无助于我们真正实现这些需求。

请注意，端到端原则并非总是成立的证明或定理。它是一种指导原则和哲学论证，不同的设计师可能会提出不同的支持或反对该原则的论据。

以下是一个端到端原则并非绝对规则的例子。尽管端到端原则要求仅在终端主机上实现可靠性，但我们仍然可以在端到端检查的基础上，在网络中增加一些额外的可靠性措施。如果链路可靠性极低，这样做就非常有用。假设 A 和 B 之间有 10 条链路，每条链路的故障率为 10%。那么，每次发送数据包时，数据包有 65% 的概率被丢弃。但是，如果修改每个路由器，使其发送两份数据包以提高可靠性，那么每条链路的故障率仅为 0.1%，数据包的丢弃概率也降至 1%。无线链路有时会通过增加可靠性来降低错误率，从而提高终端主机的性能。

端到端原则也适用于其他领域。例如，在安全领域，端到端原则可能意味着通信的两个终端主机应该在终端主机上加密消息，而不是在网络中的中间节点进行加密。

## 路由

我想我们不用再重述邮件收发室、秘书和老板了，但是我们一直忽略了邮政公司是如何工作的。我们究竟是怎样架设起连接全球的互联网的？

假设机器 A 和机器 B 都连接到互联网。机器 A 想要向机器 B 发送一条消息，但这两台机器之间并没有直接连接。机器 A 如何知道将消息发送到哪里，以便消息最终到达机器 B？消息将通过哪条网络路径到达目的地机器 B？在本块内容中，我们将学习**路由**来回答这些问题。

路由所解决的问题：当路由器接收到一个数据包时，路由器如何知道将数据包转发到哪里，以便最终到达最终目的地？
路由本质上是一个图论问题，在不考虑自治系统特殊策略的情况下，路由拓扑应构成一个满足最小成本路由原则的有向无环图（DAG）。我们并不需要了解那么深，只需要感性认识路由的概念就好。

还记得第一块我们讲的邮政系统吗，假如一个包裹要送到中国辽宁省大连市大连理工大学西山学生生活区7舍320，商家把这个快递投到最近的邮局之后，快递员要根据这个邮局保存的邮政线路图投到尽量靠近终点的下一个邮局。举个例子，如果下一个邮局可以选择大连市邮局或者大连理工大学西山学生生活区7舍丰巢柜，那默认一定会选择后者。用术语来讲，数据包到达一个路由器（邮局）后会根据该路由器所维护的路由表规则（邮政线路图），根据最长前缀匹配（尽量选择最匹配目标地址）来确定下一跳路由器（或终端）。当路由器接收到数据包时，路由器会查看其目标 IP，并使用转发表选择一条链路来转发数据包。简单来说，根据收货地址，将快件尽可能地送往更详细的更靠近终点的地址。这就是路由的原理，我们基于此构建了互联网。

在此我们还简单区分一下路由器与路由。路由是路由器的其中一个功能，现代路由器还能提供包括但不限于dhcp等服务。我们所做的软路由实验就是不使用普通路由器中厂家烧录好的系统，而是在路由器或主机等设备上刷入软路由系统以期开发使用一些其他服务。

我们上面的讨论一直基于不考虑自治系统特殊策略，实际上，这些路由服务提供商为了商业效益肯定会隐藏自己网络拓扑，并根据客户的合同为客户选择不同品质的路由服务。同时，恶意 AS 可能会撒谎，并通告一条通往目的地的路由，即使该 AS 无法到达该目的地。恶意 AS 还可能通告一条通往目的地的非常廉价的路由，即使这条廉价路由实际上并不存在。这可能会鼓励其他 AS 通过恶意 AS 路由数据包，而攻击者可以删除或修改经过恶意 AS 的数据包。这些攻击被称为**前缀劫持**。

你可能会好奇路由表如何构造，这里仍然强烈建议你阅读UC Berkley开设的CS168计算机网络基础课程教材。

## IP（地址）

网络上的每台主机（例如您的计算机、科中的服务器）都会分配一个 IP 地址。在本部分中，您可以假设每台主机都有一个唯一的 IP 地址。
IP**地址**是唯一标识主机的数字。就像邮政系统一样，IP地址的选择也包含一些关于主机所在位置的信息。
请注意，IP 地址不一定是静态的。打个比方，如果您搬到了另一所房子，您的地址就会改变。同样，如果您的计算机移动到其他位置，它在加入网络时可能会被分配一个不同的 IP 地址（并且您的旧 IP 地址最终会过期）。
IP 地址的长度取决于所使用的 IP 版本。IPv4 地址为 32 位，而 IPv6 地址为 128 位。两个版本的路由概念相似，但我们会尽可能使用 IPv4，因为地址越短，越易于阅读。

这里我们略过CIDR的介绍，关于ip寻址方法的发展历程你仍然可以在UC Berkley开设的CS168计算机网络基础课程教材中找到答案。我们直接介绍IP与子网掩码的编写规则。

为了便于阅读，我们取每个 8 位序列，并将其写成一个整数（介于 0 到 255 之间）。例如，IP 地址 00010001 00100010 10011110 00000101 可以写成 17.34.158.5。有时，这种表示法也称为**点分四组**表示法。要编写子网掩码，我们将所有固定位写为 1，所有非固定位写为 0，然后将结果转换为点分四组。例如，如果范围是 192.168.1.0/29，我们可以写 29 个 1（固定位）和 3 个 0（非固定位）。11111111 11111111 11111111 111111000 用点分四组表示为 255.255.255.248。网络掩码表示法的范围是 192.168.1.0，子网掩码为 255.255.255.248。实际上，网络掩码很有用，因为给定一个特定的 IP 地址，如果对 IP 地址和网络掩码进行按位与运算，所有主机位都会被清零，只保留网络位。换言之，如果得到的地址相等，则它们属于同一网络。

IPv4 地址是 32 位的，这意味着我们大约有 40 亿个可用地址。这够用吗？

## 协议与应用

### （一）NAT（连接局域网与公网的桥梁）

在刚才对IP的介绍中，我们知道了我们只有2^32种不同的IPv4地址，不足以覆盖互联网上的所有主机。我们已经看到 IPv6 是解决 IPv4 地址枯竭问题的可靠解决方案，但 IPv6 的普及速度相当缓慢。与此同时，为了节省地址空间，请记住，IANA 分配了特殊的 RFC 1918 私有 IP 地址范围，这些地址可供任何不需要互联网地址的网络使用：192.168.0.0/16、10.0.0.0/8 和 172.16.0.0/12。事实证明，这些地址也经常用于您的家庭网络，因此您的个人设备不需要唯一的 IP 地址。但是，您确实需要互联网接入，那么如何使用私有 IP 地址呢？

应用NAT，我们能使用单个公共IP地址来代表本地网络中的多台主机。这可以理解为你的高中学校要求你把录取通知书统一邮到学校，之后学校分发给个人。路由器会生成一个NAT表，将路由器LAN口WAN口的用户请求源IP与端口形成映射关系。这样局域网内主机的请求在目标服务器看来就是经过路由器的一个公网IP，实际上发回到路由器后由NAT表映射会局域网IP与端口发回到终端主机。

经常联机玩MC或星露谷等游戏的玩家可能听说过内网穿透这个概念，其实这就是一种绕过NAT的方式。由此可见，NAT某种程度上会阻止外部对内部资源的访问，即默认情况下不允许入站连接。这可以被视为一项安全功能，尽管它更像是一种副作用，而非刻意为之的设计。NAT 还有一个副作用，就是它可以帮助保护客户端的隐私。同样，这并非一个刻意为之的安全功能。由于路由器会重写客户端的 IP 地址，因此当服务器收到数据包时，它无法知道原始发送者的身份。

### （二）DNS（应用层）

还记得上面讲到过的网络地址IP吗，很容易发现在日常生活中我们访问网络资源很少直接使用ip地址，而是使用url访问网络资源。问题在于我们之前构建的网络拓扑中用于寻址的报头中包含的是ip地址，终端机器是怎么知道url对应的ip地址的？

受历史因素影响，DNS是一个分布式系统，根据区域将所有名称服务器排列成树状层次结构。DNS查询始终从根服务器出发。根服务器会将您的查询定向到其子域名服务器之一。然后，您向子域名服务器发出查询，该域名服务器会将您重定向到其子域名服务器之一。此过程重复进行，直到您向知道答案的域名服务器发出查询，该域名服务器将返回与您的域名对应的 IP 地址。

设想一下，如果有一个旁路系统发送比真实的DNS回应更早到达攻击目标的伪造DNS回应，将请求重定向至空路由或者恶意网站IP，这种行为就被称为网络钓鱼。

设想一下，如果有一个中介假DNS服务，黑名单检测域名中关键字，对某些域名请求重定向至空路由，对其他请求则递交上级DNS服务器，这样你就发明了拦截广告、恶意网站和跟踪器的方法。AdGuardHome方案便采取这种策略。上网请求实际分两步，第一步，通过DNS解析域名返回目标服务器IP，第二步，通过IP建立到远程服务器的TCP连接，使用HTTP传送内容。域名方式就是在DNS做文章，发现请求是广告请求就直接返回域名不存在或者一个无效IP，阻止TCP连接建立。这种方式优点在于简便，快速，不介入正常TCP连接。缺点是DNS只能获得域名，却不能获得完整的URL地址，因此无法对一些URL特征进行过滤。好在现在广告普遍都是植入式，也就是普通站点嵌入一个指向广告的链接，通常广告都有相对清晰的域名（通常广告域名与访问站点域名不通），所以可以取得不错的效果。这也是现在绝大多数方案的原理。

## 端对端

***为了接下来的故障排查实验，我们将以计算机第一次入网并请求访问[thbwiki.cc](https://thbwiki.cc/)为例，逐步演示发生的情况。在此过程中，我们将了解网络的各个部分如何协同工作以处理用户的请求。当然，只需要感性理解流程，在这里我们将提供专业性质的讲义。***

#### 步骤1：通过DHCP获取网络配置

计算机启动并接入以太网后，由于尚未获得任何网络配置信息，会广播一条 DHCP 请求。假设家庭路由器充当 DHCP 服务器（这在家庭网络中十分常见），路由器将以单播形式回复一个包含网络配置的 offer。该配置信息包括子网掩码、默认网关的 IP 地址、DNS 服务器地址，以及一个可用的 IP 地址。随后，计算机会发送确认消息，完成 DHCP 分配过程，服务器回复确认信息。

#### 步骤2：使用ARP获取路由器的MAC地址

通过 DHCP 获取到路由器的 IP 地址后，转发表指示所有非本地数据包应发往该路由器。在向外部服务器（如 DNS 或thbwiki服务器）发送数据前，需先获取路由器的 MAC 地址，以便在本地网络内正确寻址。

首先确认路由器 IP 地址（如 192.168.1.1）属于本地子网（例如 192.168.1.2/24），说明路由器位于同一局域网内。通过广播 ARP 请求，询问该 IP 对应的 MAC 地址，路由器将回复其 MAC 地址（例如 01:ab:cd:ef:42:01）。系统会缓存该 IP-MAC 映射，后续发往外部网络的数据包均使用此 MAC 地址作为目标，无需重复进行 ARP 请求。

#### 步骤3：执行DNS查询

获得网络配置后，需解析 thbwiki.cc的 IP 地址。操作系统在浏览器调用类似 `getaddrinfo`的函数后触发 DNS 查询。DNS 服务器地址（例如 8.8.8.8）由 DHCP 提供，且不在本地网络中，因此需将 DNS 请求发往路由器。

逐层构建 DNS 请求数据包：

- 应用层（第7层）：在 DNS 问题字段中添加对 `链接1`的 A 记录查询，并填写包头信息（如事务ID、记录数等）。
- 传输层（第4层）：DNS 使用 UDP 协议。源端口由客户端任意选择，目标端口为 53。
- 网络层（第3层）：源 IP 为 DHCP 分配的地址，目标 IP 是 8.8.8.8。
- 数据链路层（第2层）：源 MAC 为计算机硬件地址，目标 MAC 为路由器的 MAC 地址（通过 ARP 获得）。

数据包发送后，若网络采用 NAT，路由器会改写 UDP/IP 包头，将私有 IP 转换为公网 IP。递归解析器若未缓存结果，会进一步向权威域名服务器查询，最终将包含 IP 地址的 A 记录返回给客户端。

#### 步骤4：建立HTTP连接

获得服务器 IP 后，浏览器尝试与其建立 HTTP 连接。由于 HTTP 基于 TCP，需先完成 TCP 三次握手：客户端发送 SYN，服务器回复 SYN-ACK，客户端再回复 ACK，此时双向字节流通道建立。

构建 HTTP 请求包：

- 应用层：方法为 GET，请求资源为 `/`，协议版本为 HTTP/1.1。
- 传输层：运行于 TCP 之上。浏览器可使用操作系统分配的临时端口作为源端口，目标端口为 80。
- 网络层：源 IP 为本地地址，目标 IP 为thbwiki服务器的地址（通过 DNS 查询获得）。
- 数据链路层：源与目标 MAC 地址与之前 DNS 请求相同。

服务器返回状态码为 200 OK 的 HTTP 响应，消息体为网页 HTML 内容。浏览器通过套接字读取字节流，根据 Content-Length 或分隔符解析响应。若 HTML 中包含其他资源（如图片或链接），可能触发后续 HTTP 请求。为提高效率，对同一服务器的多个请求可通过同一 TCP 连接以流水线方式发送。

完成所有请求后，通过 FIN-ACK 过程正常关闭连接。

需要注意的是，HTTP 请求与响应可能被拆分为多个 TCP 数据包传输，各包网络层和传输层头相同，但序列号不同，最终在应用层重组为完整消息。因此，一个 HTTP 事务不再与单个网络包一一对应。
